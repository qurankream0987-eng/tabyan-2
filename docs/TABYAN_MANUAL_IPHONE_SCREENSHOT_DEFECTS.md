# تقرير إصلاح عيوب صور iPhone — Tabyan Native

**التاريخ:** 14 سبتمبر 2026  
**النطاق:** بوابة Admin/Supervisor Native والعيوب الظاهرة في صور iPhone، دون بدء Build 6 ودون تعديل QCF أو WebRTC.

## الملخص التنفيذي

تم إصلاح العيوب البرمجية التي يمكن إثباتها من الكود والاختبارات:

- إخفاء مسار الفتاوى عن المعلم غير المصرح له، مع إبقاء الحارس الخادمي.
- جعل مستويات placement مرتبطة بمسار الطالب، ومنع اعتماد مستوى غير نشط أو من مسار مختلف.
- منع بقاء `levelId` قديمًا عند تغيير المسار أو المادة، وإظهار تسمية مستويات Tajweed الترتيبية في نموذج إدارة الحسابات.
- تحسين عرض حقول كلمة المرور في تسجيل الطالب دون تغيير قواعد التحقق.
- إصلاح دورة كاميرا placement: المعاينة تظهر بعد التسجيل فقط، وإعادة التسجيل تعيد فتح الكاميرا.
- إضافة حماية Safe Area إلى شاشة المراجعة ومحتوى الشاشات، مع تمرير نموذج المراجعة على iPhone صغير.

لم يُعلن نجاح تشغيل فيديو placement في الإنتاج؛ لأن نقطة التخزين خاصة وتتطلب جلسة مستخدم مصادقًا عليها، ولم يكن من المسموح اختلاق token أو استخدام fallback غير موثق.

## الإصلاحات المنفذة

### الفتاوى والصلاحيات

- تعتمد الوجهة والبلاطة السريعة على `teacher.kycStatus` و`isMufti === true`.
- يظل الحارس الخادمي قائمًا، لذلك إخفاء الواجهة ليس بديلًا عن authorization.

### Placement levels

- أضيفت نقطة `placementLevelThresholds` بمسار مطلوب (`quran` أو `tajweed_correction`).
- قائمة المراجعة Native تستدعي المستويات المرتبطة بمسار الطلب فقط.
- `placementReview` يرفض:
  - الاعتماد دون مستوى.
  - الطالب الذي لا يملك مسار placement محددًا.
  - مستوى غير نشط.
  - مستوى لا يطابق مسار الطالب.
- يُعاد استخدام المستوى المقبول عند إنشاء `studentProgress`.

### إدارة الحسابات

- عند اختفاء المسار المختار من البيانات النشطة، يعود النموذج إلى أول مسار متاح ويمسح المستوى.
- عند تغيّر المادة أو المسار بحيث لا يعود المستوى الحالي صالحًا، يُمسح `levelId`.
- مستويات Tajweed تعرض بأسماء ordinal عربية بدل خلط مستويات المسارات الأخرى.

### تسجيل الطالب والكاميرا

- أضيفت labels عربية ثابتة لحقلي كلمة المرور.
- أزرار إظهار/إخفاء كلمة المرور لها accessibility labels مستقلة ولا تتداخل مع الحقول.
- قاعدة كلمة المرور: محرف واحد غير مسافة على الأقل، مع إبقاء التأكيد المطابق.
- بعد التسجيل، تُزال الكاميرا الحية وتظهر المعاينة بنسبة 3:4.
- زر إعادة التسجيل يمسح المعاينة ويعيد فتح الكاميرا.
- أضيفت مساحة أسفل المحتوى تعتمد على Safe Area لتفادي تغطية الأزرار بمؤشر iPhone السفلي.

## التحقيق الجنائي لفيديو الإنتاج

### بيانات قاعدة الإنتاج

تمت قراءة قاعدة الإنتاج للعرض فقط. توجد سجلات placement فعلية بمسار `quran` وروابط private object، منها سجلات بحالة `pending`. لا توجد نتيجة تثبت أن الملف قابل للتشغيل من دون مصادقة.

### طلبات HTTP الفعلية

تم اختبار رابط object من النطاق المنشور:

- `GET` دون Authorization: `401`
- `HEAD` دون Authorization: `401`
- `GET` مع `Range: bytes=0-1023` دون Authorization: `401`
- `Content-Type` للاستجابة غير المصرح بها: `application/json; charset=utf-8`
- `Content-Length`: `24`

هذه النتائج تثبت بوابة authorization فقط. لم نصل إلى `Content-Type` الحقيقي للفيديو أو `Content-Length` الحقيقي أو `Accept-Ranges` أو اختبار Range ناجح، لأن ذلك يتطلب token إنتاج صالحًا لحساب مالك الفيديو أو حساب admin. لذلك لا يمكن تصنيف المشكلة كـ storage missing أو content-type أو range، ولا يمكن إعلان نجاح playback.

## ما بقي مطلوبًا قبل PASS النهائي

1. اختبار على iPhone فعلي:
   - طلب الكاميرا والميكروفون.
   - بدء التسجيل وإيقافه.
   - المعاينة وإعادة التسجيل.
   - اتجاه الجهاز وSafe Area.
   - رفع الفيديو ثم ظهوره في Admin.
2. تنفيذ طلب authenticated فعلي لفيديو placement production مع تسجيل:
   - `HTTP_STATUS`
   - `CONTENT_TYPE`
   - `CONTENT_LENGTH`
   - `ACCEPT_RANGES`
   - ثبات Authorization بعد أي redirect.
   - نتيجة طلب Range.
3. عدم بدء Build 6 أو النشر قبل اكتمال بوابة الجهاز الفعلي وفحص playback المصادق عليه.
