# دراسة معمارية عالية المستوى لنظام تبيان

**النطاق:** قراءة بنية المستودع وتوثيقها على مستوى عالٍ فقط. هذه ليست مراجعة تفصيلية أو خطة تنفيذ.

## خلاصة

المستودع monorepo يستخدم pnpm workspaces ويضم واجهة ويب رئيسية، تطبيق Expo Native واحداً، معاينة ويب منفصلة للمعلمين والإشراف، وخادم API. تتصل واجهات الويب وNative بخادم مشترك عبر tRPC؛ وتوجد قاعدة PostgreSQL واحدة ممثلة بمخطط Drizzle مشترك. يضم الخادم أيضاً مسارات HTTP وWebSocket للتخزين والتلاوة والاتصال الآني.

البنية المستهدفة في المواصفة — Student Native وStaff Native وWeb فوق Backend وبيانات مشتركة — ممكنة منطقياً إذا بقيت قواعد العمل والهوية والبيانات في الخدمات المشتركة. لكنها ليست بنية التطبيقات الحالية: دورا المعلم والإشراف موجودان حالياً في الويب وتطبيق Native نفسه، أما واجهة TABYAN STAFF الموجودة فهي معاينة ويب. وفي مساحة العمل الحالية قيد موثّق على عدد تطبيقات Expo/Native؛ لا ينبغي افتراض أن حذف معاينة Staff يتيح إنشاء تطبيق Native ثانٍ هنا.

## 1. بنية المستودع الحالية

- `artifacts/tabyan`: تطبيق React/Vite للويب.
- `artifacts/mobile`: تطبيق Expo/React Native يستخدم Expo Router.
- `artifacts/tabyan-staff-preview`: تطبيق React/Vite منفصل لمعاينة واجهات المعلمين والإشراف.
- `artifacts/api-server`: خادم Express.
- `lib/db`: اتصال PostgreSQL ومخطط Drizzle.
- `lib/tabyan-trpc`: سياق الخادم ووسطاؤه وموجّه tRPC وإجراءات الأدوار.
- `lib/tabyan-domain`: حزمة مجال مشتركة صغيرة نسبياً، تحوي عقوداً ومساعدات مشتركة.
- `lib/api-spec`, `lib/api-zod`, `lib/api-client-react`: مواصفة OpenAPI وأدوات التحقق والعملاء المولّدة.
- `lib/design-tokens`: رموز التصميم المشتركة.
- إدارة الحزم مركزية عبر pnpm workspaces؛ توضح ملفات الحزم استخدام TypeScript وReact وExpo وExpress وDrizzle.

## 2. علاقة الويب وNative والخادم

يهيئ `artifacts/api-server/src/app.ts` خادم Express ويوصل:

- مسارات HTTP تحت `/api`، ومنها الصحة والتشخيص والتخزين.
- موجّه `appRouter` من `@workspace/tabyan-trpc` تحت `/api/trpc`.
- نقاط اتصال WebSocket للتلاوة الفورية والإشارات في وحدات منفصلة بالخادم.

يوجد في Web وNative عميل tRPC موجّه إلى `/api/trpc`. وتستخدم معاينة Staff أيضاً tRPC وعقد `AppRouter` المشترك. يعتمد الخادم على `@workspace/db`؛ وتستعمل الحزمة PostgreSQL وDrizzle. لا تتصل واجهتا العميل مباشرة بقاعدة البيانات حسب البنية التي تمت معاينتها.

توجد كذلك مجموعة OpenAPI مولّدة إلى جانب tRPC. وجودها لا يثبت وحده وجود تكرار فعلي للعمليات، لكنه يجعل توحيد العقود والتأكد من تماثل السلوك بين الواجهات موضوعاً مناسباً لتدقيق لاحق.

## 3. وحدات الطالب

- الويب: `artifacts/tabyan/src/pages/student`، بما فيه الصفحة الرئيسية، المسارات والمستويات، المكتبة، الفتاوى، الجدول، التلاوة وسجلها، والاختبار التمهيدي.
- Native: `artifacts/mobile/app/student`، مع مسارات للمصادقة والصفحة الرئيسية والمكتبة والمستويات والقرآن والتلاوة والاختبار والجلسات والإشعارات والحساب.
- يشمل الطرفان شاشات وتدفقات طالب، لكن سلوك كل منصة ليس بالضرورة متطابقاً.
- توجد في الويب صفحة مصحف مخصصة `MushafFahd.tsx` ووحدات للمصحف. لم يُجر هذا الاستطلاع تدقيقاً لمسار المصحف Native؛ لذلك لا يفترض وجود تكافؤ بينهما.

## 4. وحدات المعلم

- الويب: `artifacts/tabyan/src/pages/teacher`، مع صفحات للطلاب والتقييمات والجدول والجلسات والإشعارات وغيرها.
- Native: `artifacts/mobile/app/teacher`، مع مجموعات فرعية للطلاب والتقييم والإشعارات والجلسة.
- واجهة معاينة Staff المنفصلة تطبيق ويب، وليست تطبيق Native للمعلم.

## 5. وحدات المشرف والإدارة

- الويب: `artifacts/tabyan/src/pages/admin` يضم إدارة المستخدمين والطلاب والمعلمين والجداول والمستويات والتقييمات والإشعارات والتدقيق وغيرها.
- Native: توجد مجموعة `artifacts/mobile/app/admin` إلى جانب مسارات الطالب والمعلم.
- يتشارك المعلم والمشرف نطاق Staff، لكن المسارات والإجراءات تفصل بينهما بدرجات صلاحية مختلفة؛ لم يُدقّق هذا الاستطلاع صلاحية كل إجراء أو حارس دور.

## 6. التصنيف عالي المستوى

| التصنيف | أمثلة حالية |
|---|---|
| `STUDENT_ONLY` | مسارات الطالب في الويب و`artifacts/mobile/app/student` |
| `TEACHER_ONLY` | صفحات وموجّهات المعلم، مثل `pages/teacher` و`app/teacher` |
| `SUPERVISOR_ONLY` | صفحات الإدارة ومساراتها، مثل `pages/admin` و`app/admin`؛ يلزم تدقيق صلاحيات كل مسار لتأكيد حدودها |
| `STAFF_SHARED` | معاينة Staff ومسارات المعلم والإدارة ذات الاستخدام المشترك؛ يختلف الوصول بحسب الدور |
| `ALL_CLIENTS_SHARED` | واجهة tRPC وعقودها، مخطط البيانات المشترك وبعض رموز التصميم؛ ليس كل ملف مشتركاً بين كل عميل |
| `BACKEND_ONLY` | خادم Express، الوصول إلى قاعدة البيانات، عمليات التخزين ومهايئات خدمات التلاوة |
| `WEB_ONLY` | تطبيق الويب الرئيسي ومعاينة Staff ووحدات واجهة المتصفح، ومنها صفحة المصحف المخصصة |
| `NATIVE_SHARED` | تطبيق Expo واحد يحوي بوابة المصادقة ومسارات أدوار متعددة، ووحدات Native مثل مسجل الجلسات |
| `UNKNOWN` | التفاصيل التشغيلية الدقيقة لموفري الذكاء الاصطناعي النشطين، وحدود التكافؤ والصلاحيات، وما إذا كانت كل عقود OpenAPI مستخدمة حالياً |

## 7. القرآن وTabyan AI والوسائط والوقت الآني

- **القرآن والمصحف:** تتضمن واجهة الويب صفحة المصحف ومجلدات مكونات وأصولاً مرتبطة به. توجد كذلك صفحات ومسارات للقرآن والتلاوة والتعلم في العملاء. لا يثبت وجود بيانات أو مكونات متشابهة تطابق التنفيذ بين Web وNative.
- **التلاوة وTabyan AI:** يحتوي المستودع وحدات تلاوة على العميل، وعقوداً مشتركة، ومهايئات خادم لموفّرين مثل OpenAI وSpeechmatics وNVIDIA وNabr وTarteel، مع وحدات WebSocket. هذه الأدلة تثبت وجود بنية تكامل للتلاوة؛ ولا تثبت أن جميع الموفّرين مفعّلون أو أن هناك منتج AI مستقلاً مكتملاً.
- **النماذج الكبيرة:** لم يعثر المسح الاسمي المحدود لمجلدَي Web وNative على ملفات أوزان بامتدادات شائعة مثل `.onnx` أو `.gguf` أو `.safetensors` أو `.pt` أو `.tflite`. هذا ليس تدقيقاً شاملاً لكل طريقة تضمين أو تخزين، ولا قياساً لحجم التطبيق. اتجاه المواصفة المستقبلية هو استدعاء Tabyan AI عبر API والخدمات الخلفية، لا تضمين نموذج كبير في تطبيق الطالب.
- **الوسائط:** لدى الخادم وحدات تخزين وصلاحيات ووسائط خاصة، ويعتمد على عميل تخزين سحابي. توجد وحدات رفع وتخزين على العميل. ينبغي بقاء ملكية الملفات والتحقق منها وسياسات الوصول والحذف في الخدمات الخلفية.
- **التنبيهات والجلسات:** توجد موجّهات للإشعارات والجدولة والجلسات، إلى جانب قنوات اتصال آني على الخادم. تفاصيل اعتماد كل عميل عليها تحتاج تدقيقاً منفصلاً.

## 8. نقاط الاقتران الظاهرة

1. تطبيق Native واحد يجمع الطالب والمعلم والإدارة في شجرة مسارات Expo نفسها؛ وهذا اقتران عرض وتغليف واضح.
2. تطبيق الويب الرئيسي يجمع صفحات الطالب والمعلم والإدارة داخل تطبيق واحد.
3. موجّه tRPC الجذري يجمع موجّهات المصادقة والطالب والمعلم والإدارة والتلاوة وغيرها، وتستهلكه واجهات متعددة.
4. مخطط Drizzle واحد يحتوي سجلات الطلاب والمعلمين والجلسات والتقييمات والتقدم والإشعارات وبيانات أخرى؛ فصل التطبيقات لا يعني فصل قاعدة البيانات.
5. يوجد مساران للعقود: tRPC، ومواصفة OpenAPI مع عميل ومخططات مولّدة. يجب تحديد أي العمليات authoritative وتجنّب تباعد التعريفات.
6. حزمة المجال المشتركة موجودة، لكن قائمة ملفاتها المرئية أصغر من كامل منطق المنتج؛ لا ينبغي افتراض أن جميع قواعد القرآن أو الصلاحيات نُقلت إليها بالفعل.
7. معاينة Staff واجهة ويب منفصلة تشارك API، بينما تظل شجرة Staff الأصلية موجودة أيضاً في التطبيقين الرئيسيين. هذا يخلق أكثر من مكان عرض لنفس أدوار الاستخدام، ويستحق تحديد دور كل واجهة قبل الفصل.

هذه نقاط اقتران بنيوية لا أحكام على وجود خلل. لم يُفحص كل استيراد أو مسار أو اختبار.

## 9. البنية المستقبلية المقترحة في المواصفة

```text
                    Tabyan Backend
                   /       |       \
          Student Native  Staff Native  Web Platform
                   \       |       /
          هوية وصلاحيات وبيانات مشتركة
```

يمكن تنظيم المستودع مستقبلاً حول تطبيقات الويب والطالب Native وStaff Native، مع حزم مشتركة للعقود والمجال والقرآن والصلاحيات وواجهة المستخدم، وخدمات API وAI والوسائط. هذا تصور لا توصية بنقل ملفات الآن. التطبيق الأنسب هو إبقاء منطق المجال والعقود والتحقق والوصول للبيانات على الخادم أو في وحدات مشتركة صريحة، وترك واجهات العملاء مسؤولة عن العرض وسلوك المنصة.

## 10. مبادئ البيانات المشتركة

- قاعدة بيانات ومخطط بيانات authoritative واحد؛ لا قاعدة مستقلة لكل تطبيق.
- هوية ودور وصلاحية موحّدة يتحقق منها الخادم لكل طلب، لا مجرد إخفاء روابط الواجهة.
- تستمر العلاقات بين الطالب والمعلم والجدول والجلسة والتقييم والتقدم في نماذج البيانات الحالية.
- تظل قواعد ملكية الوسائط والوصول الخاص والحذف والتحقق من الملفات على الخادم.
- تمر مخرجات التلاوة/الذكاء الاصطناعي عبر عقود واضحة تربط المستخدم والجلسة والمصدر والنتيجة، بدلاً من منطق مستقل في كل واجهة.
- يجب أن تشترك الواجهات في API contracts وقواعد تحقق مستقرة مع اختبارات اتساق.

## 11. مخاطر فصل التطبيقات

- اختلاف الهوية أو الأدوار أو الصلاحيات بين عميلين قد يكشف بيانات أو يمنع إجراءات مشروعة.
- نسخ قواعد القرآن أو الجلسات والتقدم إلى كل عميل يسبب نتائج متعارضة وصعوبة إصلاحها.
- اختلاف عقود tRPC وOpenAPI أو توليد عميل قد يؤدي إلى انحراف بين Web وNative.
- نقل واجهات Staff دون نقل متطلبات الجلسات والإشعارات والوسائط وصلاحيات التقييم قد يكسر تدفقات مترابطة.
- إعادة توزيع عمليات الوسائط أو التلاوة الفورية قد تفقد فحوص الملكية أو حدود الاستخدام أو أثر التدقيق.
- فصل الشاشات لا ينبغي أن يحذف سجلات أو إجراءات مفيدة للويب أو Staff.
- تطبيق Expo/Native ثانٍ يواجه قيد Artifact موثقاً في مساحة العمل الحالية؛ يلزم مسار أو مشروع آخر إذا استمر القيد.
- لا يمكن تقدير حجم IPA/APK من هذا الاستطلاع؛ يتطلب ذلك قياس نواتج بناء معتمدة، وهذا خارج النطاق.

- المصادقة والأدوار والصلاحيات وفصل بيانات الحسابات.
- تطبيق الطالب Native وتدفقاته واختلافاته عن الويب.
- مسارات القرآن والمستويات والمصحف ومصدر بيانات النص والأصول.
- اختبار القبول والتسجيل والوسائط المرتبطة به.
- التلاوة وTabyan AI: العميل، موفرو الخدمة، اختيار النموذج، شروط الاستخدام والتكلفة.
- الجلسات والاتصال الآني والتسجيل والتنبيهات.
- واجهات المعلم على Web وNative.
- واجهات المشرف والإدارة على Web وNative.
- التخزين ورفع الملفات وملكية الوسائط وسياسة الحذف.
- عقود OpenAPI مقابل tRPC واستخدامات كل عقد.
- تحضير Staff Native واستراتيجية إصداره خارج قيد Artifact الحالي.

## حدود الدراسة والإجراءات

استندت الدراسة إلى قوائم المجلدات وملفات تعريف الحزم ونقاط الدخول والربط الرئيسية. لم يُجر تدقيق شامل للملفات أو الحقوق أو النشر أو قاعدة بيانات حية، ولم يُقَس حجم حزمة تطبيق.

- **ملفات التنفيذ المعدلة:** لا.
- **ملفات محذوفة:** لا.
- **قاعدة البيانات:** لم تتغير.
- **الحزم:** لم تتغير ولم تُثبّت.
- **الإعدادات:** لم تتغير.
- **Build أو اختبارات:** لم تُشغّل.
- **النشر:** لم يحدث.
- **التنفيذ:** لم يحدث.
- **الملف الوحيد المنشأ:** `research/TABYAN_SYSTEM_ARCHITECTURE_STUDY.md`.
- **الخطوة التالية:** انتظار اختيار المستخدم لأول مجال يريد تدقيقه بعمق.
