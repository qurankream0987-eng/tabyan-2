# TABYAN Ready Smart Mushaf Ecosystem Audit

**Research date:** 2026-10-15  
**Depth:** Deep  
**Sources consulted:** 52
**Scope:** Source-level evaluation of the three alheekmahlib repositories and their packages, rights boundaries, QRC protocol, and Flutter/Expo hosting options. No candidate code, model, or third-party asset was imported. No live provider call, database mutation, or deployment occurred.

## Executive Summary

The three repositories form a useful reference ecosystem, but they are not a single drop-in product. The alquranalkareem app depends on `quran_library`; its checked-in manifest does not depend on `quran_audio`. GitHub reports no detected license for the app repository, while the standalone `quran_library` and `quran_audio` software packages publish MIT licenses. The `quran_library` notice explicitly excludes QCF fonts and QUL/KFGQPC resources from the code license. The package release page and main branch also differ: pub.dev reports 5.0.1, while the current repository manifest says 5.0.2. Pin an exact release before any implementation. **FINAL DECISION: ADOPT_WITH_ADAPTER.** Evaluate only the MIT-licensed `quran_library` software surface in an isolated Flutter candidate, behind a Tabyan adapter that preserves Tabyan authentication, backend, data ownership, branding, and educational policy. Do not reuse the unlicensed parent app, port `quran_audio`’s current QRC client, ship unclear Quran assets, or charge for features powered by the NPL model. Keep Tabyan’s current Web Mushaf, QCF v2 data, routes, auth, and backend unchanged. This is an architecture recommendation, not approval to distribute uncleared content.

## Background and Method

The audit treats each repository as a separate unit: the app repository is not assumed to grant rights to its dependencies; a package’s code license is not assumed to cover its downloaded models or Quran assets; and a provider guide is not treated as proof that an implementation works live. GitHub branch sources and package release metadata are compared explicitly because the package and repository can differ. The audited repository branch is mutable, so a future implementation must pin a commit or published package version rather than depend on `main`. [[3]](https://api.github.com/repos/alheekmahlib/alquranalkareem) [[5]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/pubspec.yaml) [[6]](https://pub.dev/api/packages/quran_library) [[18]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/pubspec.yaml) [[19]](https://pub.dev/api/packages/quran_audio)

The report distinguishes **source-verified** behavior from **runtime-verified** behavior. No model download, phone test, live QRC session, production query, data migration, or deployment was included. Public documentation was checked against saved repository files and current framework documentation. The source registry and saved evidence paths are in `research/smart-mushaf/sources.json` and `research/smart-mushaf/sources/`.

## Key Findings

### 1. Repository boundaries and reuse readiness

The parent app is the least suitable reuse target. Its manifest identifies a full Flutter product and includes `quran_library`, but not `quran_audio`; its GitHub metadata has no detected license. Treat it as a behavioral reference only unless the owner grants a separate license. The library package is the meaningful reuse unit: its README documents Quran display, audio, navigation, bookmarks, search, tafsir, and Tasmee. The separate `quran_audio` package focuses on audio playback and has a QRC module, but the parent app manifest does not establish that it is integrated into the app. [[1]](https://github.com/alheekmahlib/alquranalkareem) [[2]](https://raw.githubusercontent.com/alheekmahlib/alquranalkareem/main/pubspec.yaml) [[3]](https://api.github.com/repos/alheekmahlib/alquranalkareem) [[4]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/README.md) [[20]](https://github.com/alheekmahlib/quran_audio) [[18]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/pubspec.yaml) [[19]](https://pub.dev/api/packages/quran_audio)

The `quran_audio` manifest and pub.dev page both report 1.0.0, uploaded 2026-07-11. ### 2. Quran rendering and Tasmee capabilities

The code contains a page-oriented Quran screen and a QPC V4 word renderer. During Tasmee, the renderer can hide words and style the current or completed span; the implementation uses Quran-specific font/text structures rather than a generic speech transcript. The rendering evidence supports “hide/reveal” and word-state display as implemented features, but it does not establish that the package’s Quran data/font assets may be redistributed by Tabyan. [[22]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/pages/quran_pages_screen.dart) [[23]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/quran/presentation/widgets/download_fonts_page/rich_text_build.dart) [[4]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/README.md) [[8]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/NOTICE)

The local recognition path is also explicit in source. The recitation session captures mono 16 kHz PCM, converts sample values to the recognizer input, loads a sherpa_onnx Zipformer2 CTC engine, and forwards token/timing results through Quran-specific phoneme units and alignment. A reference store and range tracker convert that stream into progress and word-state updates; final reconciliation handles the session’s end state. The code therefore supports the labels **Zipformer implemented**, **phoneme tracking present**, and **live word tracking present** at source level. It does not prove model download success, quality, throughput, or a safe score for student-facing correction. [[10]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/recitation_session.dart) [[11]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/sherpa_zipformer_engine.dart) [[24]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/quran_units.dart) [[12]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/phoneme_aligner.dart) [[25]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/core/services/tasmee_reference_store.dart) [[13]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/range_tracker.dart) [[26]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/final_reconciliation.dart)

The correction behavior needs a cautious product boundary. The source includes error detection and a madd timing heuristic, but no independent evaluation results were found. It is not safe to label this an expert tajweed teacher or to infer pronunciation correctness from a UI highlight. No teacher mode was evidenced; that remains **UNKNOWN**, not “absent from every possible branch.” [[27]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/error_detector.dart) [[28]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/engine/madd_timing.dart) [[4]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/README.md) [[29]](https://api.github.com/repos/alheekmahlib/quran_library/git/trees/main?recursive=1)

The model is fetched at runtime by the package’s model service rather than being established here as an app-bundled model. The Quran-Lab model card and the license stored with the model assets identify the Zipformer work and its terms. This audit did not fetch the weights, check a hash, or test on a phone. ### 3. QRC protocol comparison

The `quran_audio` QRC path is not a ready-made live integration for Tabyan. Its current code sends JSON text control messages and parses JSON text feedback, while the provider guide specifies MessagePack for every sent and received message. Its session records a WAV file, then sends raw 4 KiB binary fragments after the user stops; the provider expects each audio message to carry a `CHECK_TILAWA_AUDIO` method and a complete WAV file (or one raw 20 ms Opus packet). The package’s default WebSocket URL does not set `audio_format=wav`; provider documentation says Opus is the default. A custom caller-supplied URL could change that setting, but the package’s default path does not. [[32]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/qrc_client.dart) [[33]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/recitation_session.dart) [[34]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_config.dart) [[35]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_method.dart) [[36]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_feedback.dart) [[37]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/qrc_constants.dart) [[38]](https://qurani.ai/en/docs/2-advanced-tools/qrc)

There are additional wire-contract conflicts. The package emits `StartTilawaSession` and `EndTilawaSession`, while the current provider guide specifies `START_TILAWA_SESSION` and `RESET_TILAWA_SESSION`. Its feedback parser expects lowercase `start_tilawa_session` / `check_tilawa` events rather than the current `TILAWA_SESSION_STARTED` / `TILAWA_RESULT` events. Its QRC config caps `tajweed_level` at 3, while the provider guide documents hafz 1–3 and tajweed 1–5. The mismatch is visible in code; it is not a live failure report, because no provider request was made. [[35]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_method.dart) [[36]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_feedback.dart) [[34]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_config.dart) [[37]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/qrc_constants.dart) [[38]](https://qurani.ai/en/docs/2-advanced-tools/qrc)

Tabyan’s current server-side transport is better aligned with that guide. In `artifacts/api-server/src/recitation-providers/NabrQrcTransport.ts`, it uses MessagePack, sends the documented uppercase methods, processes binary MessagePack replies, and handles keepalive events. `nabr-qrc-config.ts` constructs the URL server-side with `lang=ar` and `audio_format=wav`; `nabr-qrc-audio.ts` produces 16 kHz mono 16-bit WAV frames of 200 ms, which the provider guide explicitly accepts as complete WAV messages. The API key stays in the server secret path rather than the mobile client. This is a source comparison only: no live QRC call or external result was used to validate behavior.

### 4. Rights are component-specific

The package code licenses do not clear the full stack. `quran_library` and `quran_audio` each have MIT code licenses, but the `quran_library` NOTICE expressly says QCF fonts and QUL/KFGQPC resources are governed by their own terms. That notice also summarizes a no-distracting-ads condition for apps distributing those resources; because it is the library maintainer’s summary, it is not a substitute for the primary resource terms. [[7]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/LICENSE) [[39]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/LICENSE) [[8]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/NOTICE)

The Zipformer package is a separate blocker for a paid Tabyan feature. NPL-1.2 defines the “Work” to include model weights and associated data/token artifacts, prohibits charging for the Work or features it powers (including subscriptions, paywalls, and ad revenue), permits local use, limits hosted services to free or strictly documented direct-cost recovery, and requires share-alike for derivatives. This is a plain-language summary of the supplied license text, not legal advice. Until legal review or a different model is approved, do not monetize or distribute a Zipformer-powered Tabyan feature. [[14]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/assets/quran_lab/LICENSE-QuranLab-NPL-1.2.txt) [[31]](https://huggingface.co/Quran-Lab/zipformer_p-arabic-v3/blob/main/README.md) [[30]](https://raw.githubusercontent.com/alheekmahlib/quran_library/main/lib/src/tasmee/core/services/tasmee_model_service.dart)

QUL and KFGQPC are unresolved independently. The QUL resource pages establish that fonts and Quran materials are downloadable and the October 5, 2026 changelog shows a QPC V1 font correction, but the captured pages do not grant redistribution rights. The KFGQPC terms page could not be fetched; search snippets establish resource availability only. A Quran-text repository NOTICE describes its own provenance and upstream boundaries but does not license the KFGQPC source material. Audio recordings are likewise not cleared by `quran_audio`’s MIT code license; the package lists third-party audio providers without a per-reciter recording grant. [[15]](https://qul.tarteel.ai/docs/font) [[40]](https://qul.tarteel.ai/change_logs/23) [[41]](https://qul.tarteel.ai/docs/download-resources) [[42]](https://qul.tarteel.ai/) [[16]](https://qurancomplex.gov.sa/quran-dev) [[43]](https://github.com/quran-ws/quran-text/blob/main/NOTICE.md) [[17]](https://github.com/alheekmahlib/quran_audio)

Quran Foundation API terms are a distinct regime for its APIs and returned content; they do not automatically cover QUL downloads, KFGQPC files, or the third-party recordings listed by `quran_audio`. The official terms pages fetched from both Quran Foundation hostnames concern those services, not a blanket Quran-content license. [[44]](https://api-docs.quran.com/legal/developer-terms) [[45]](https://api-docs.quran.foundation/legal/developer-terms/)

### 5. Flutter/Expo options and implementation boundary

Flutter officially supports embedding Flutter modules into native iOS and Android applications, and its documentation calls out load sequence, memory, and multi-engine costs. Expo supports custom native code through development builds, but its guidance is not a turnkey recipe for mounting a Flutter module inside the current Expo application. Combining the two runtimes would add native build, lifecycle, routing, binary-size, and platform-channel work before the candidate’s core value has been proven. [[46]](https://docs.flutter.dev/add-to-app) [[47]](https://docs.flutter.dev/add-to-app/performance) [[48]](https://docs.expo.dev/workflow/customizing/) [[49]](https://docs.expo.dev/develop/development-builds/faq/)

A dedicated Flutter candidate is the safer evaluation surface: it can reuse more of the Flutter library while leaving the current Expo app and Web Mushaf untouched. It must still rely on the Tabyan backend as the authority and use a secure, short-lived authentication handoff rather than copying third-party auth or creating a second account/data system. Universal Links and Keychain access groups are platform mechanisms, not an existing Tabyan session contract; that contract would need separate design and review. Android background-service constraints also need a physical-device test if future scope requires background recitation. [[50]](https://developer.apple.com/documentation/xcode/supporting-universal-links-in-your-app) [[51]](https://developer.apple.com/documentation/bundleresources/entitlements/keychain-access-groups) [[52]](https://developer.android.com/develop/background-work/services)

Option A (embed Flutter in Expo) is technically possible but not a first prototype here. Option B (a dedicated Flutter evaluation app/project) best isolates risk and maximizes package reuse. Option C (port only the engine into a React Native native module) would still carry the model/license issue and require separating Flutter-coupled code. Option D (move the student Mushaf experience to Flutter) is a future replacement decision, not part of the evaluation. The workspace’s single-mobile-artifact constraint and missing Flutter/Dart SDK mean none of these native implementations can be built in this current workspace without a separate hosting decision.

## Analysis

The ecosystem’s main advantage is the integrated Flutter display and recitation path, not its parent app or QRC wrapper. Reusing the package source could save substantial UI and state-machine work, but only after the exact release is pinned, asset rights are resolved, and the model terms fit Tabyan’s business model. A strict MIT-only interpretation would be incorrect because the repository itself disclaims those assets. Likewise, adopting the package’s QRC module would reduce rather than increase compatibility with Tabyan’s current server-side provider transport.

`ADOPT_WITH_ADAPTER` is the best of the four requested decision labels because it preserves the highest reusable code surface without treating every repository, model, font, recording, or authentication system as one licenseable unit. The adapter should expose only Tabyan-owned inputs and results: authenticated student/session identity, server-assigned learning range where applicable, explicit provider selection, evidence-backed word observations, and a narrow session lifecycle. It must not import the parent app’s auth/database/account model, translate uncertain recognition into a confident judgment, or change Quran text or QCF v2 data.

The final decision is conditional. For a commercial Tabyan feature, either obtain a license exception for the NPL-covered model and compatible derivatives or replace that model with one whose commercial and redistribution rights are documented. For every Quran font, text/data export, and recording, pin the exact resource and version and obtain its own permission for in-app display, offline caching, commercial use, modification, and redistribution. These clearances are prerequisites to shipping, not optional polish.

## Limitations

This was a source/document review. There was no physical iPhone or Android test, no inference run, no model download, no comparison benchmark, and no live QRC provider session. No current performance, accuracy, battery, memory, app-size, or teacher-review claim is established. QUL terms were not captured; KFGQPC terms could not be fetched; audio recording rights remain unverified. The parent app’s GitHub license metadata is null, which is not a legal opinion that no separate permission exists.

The user’s project state includes one mobile artifact, and this environment has no Flutter or Dart SDK. The candidate therefore remains a plan only. The existing Web Mushaf and QCF v2 system were not modified. The prior development-only Nabr diagnostic code remains unverified and was not exercised as part of this audit.

## Recommendations

1. Keep the present Web Mushaf, QCF v2 data, routes, and default unchanged. Do not add a Flutter view to the Expo app or switch the user-facing default during this evaluation.
2. Use the existing `quran_library` package only as the candidate’s code source after pinning the exact release/commit. Exclude the unlicensed parent app, third-party auth, and current `quran_audio` QRC implementation.
3. Keep Zipformer disabled for a paid or ad-supported feature until its NPL terms are resolved or a commercially cleared substitute is chosen. Do not download model weights during this audit.
4. Obtain rights for the exact QUL/KFGQPC fonts, Quran text/layout exports, and each audio recording before bundling, offline caching, modification, or redistribution.
5. Host the native candidate as a separate Flutter project. Use a Tabyan-owned backend/auth adapter with a reviewed short-lived token handoff; no duplicate accounts or database.
6. Make real-iPhone acceptance the first device gate: rendering and font coverage, small-screen navigation, capture interruptions, memory/battery, cold start, ASR lag, cleanup, and account isolation. Test Android only after the iPhone gate passes.
7. Revisit replacement only after rights clearance, measured device results, and explicit user approval. No change to Web/Native defaults is included in this recommendation.
