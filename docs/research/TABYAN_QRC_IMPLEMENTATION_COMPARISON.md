# TABYAN QRC Implementation Comparison

**Snapshot date:** 2026-10-15  
**Result:** **WORSE** — `quran_audio`’s current QRC implementation is materially less aligned with the provider’s current documented protocol than Tabyan’s server-side transport, based on source review only.

No QRC provider call was made. Citation numbers are shared with the ecosystem audit; Tabyan source links below are local code references.

## Summary

The `quran_audio` package contains a QRC client, but that code should not be copied into Tabyan. It uses text JSON for control and feedback, raw binary audio frames, and post-stop file upload. The current Qurani.ai guide specifies MessagePack envelopes, explicit `CHECK_TILAWA_AUDIO` messages during recording, complete WAV files or single Opus packets, uppercase methods, and uppercase result events. The package’s method names, feedback parser, audio framing, stop operation, and default audio format do not match that contract. [[32]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/qrc_client.dart) [[33]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/recitation_session.dart) [[34]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_config.dart) [[35]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_method.dart) [[36]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_feedback.dart) [[37]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/qrc_constants.dart) [[38]](https://qurani.ai/en/docs/2-advanced-tools/qrc)

Tabyan’s current backend provider transport is closer to the current guide: it holds the provider credential server-side, uses MessagePack for requests and responses, sets `lang=ar` and `audio_format=wav`, creates 16 kHz mono 16-bit complete WAV chunks of 200 ms, and sends them in `CHECK_TILAWA_AUDIO` envelopes while the recording is active. The official guide explicitly says a 200 ms WAV is acceptable if every message contains a complete WAV file. This is a static contract comparison; it does not prove that either path has been accepted by a live provider session. [[38]](https://qurani.ai/en/docs/2-advanced-tools/qrc)

## Important caveats

The provider guide is the source of the current documented protocol, not a confirmation of live availability or service correctness. The package’s default URL is bare `wss://api.qurani.ai`; callers can supply a custom URL, so the report does not claim that every possible caller would use the Opus default. The package’s own QRC control/feedback contract remains inconsistent with the guide even if a caller manually sets `audio_format=wav`. [[32]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/qrc_client.dart) [[34]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_config.dart) [[35]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_method.dart) [[36]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/lib/src/recitation/models/qrc_feedback.dart) [[38]](https://qurani.ai/en/docs/2-advanced-tools/qrc)

The package code and package version are independently licensed from audio recordings. Its README identifies third-party sources, but no per-reciter permission for commercial streaming, offline storage, or redistribution was established. [[39]](https://raw.githubusercontent.com/alheekmahlib/quran_audio/main/LICENSE) [[17]](https://github.com/alheekmahlib/quran_audio)

This comparison is **WORSE based on protocol conformity**, not a live provider acceptance verdict. Tabyan’s current QRC path also remains unverified in this turn: no new session, provider request, or external recording was created.

## Recommendation

Do not adopt `quran_audio`’s QRC client for the Smart Mushaf candidate. Preserve the Tabyan server-side QRC transport as the integration boundary, subject to a later controlled provider acceptance test and approved level semantics. Keep the key out of Flutter/Expo, retain server-owned session inputs, and use the exact documented MessagePack framing. Do not change QRC defaults or enable a production provider based on this source audit alone.
