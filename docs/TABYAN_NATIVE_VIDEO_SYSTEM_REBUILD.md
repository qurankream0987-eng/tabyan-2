# تقرير توحيد تشغيل الفيديو في Native

## الهدف

توحيد تشغيل الملفات الخاصة والمرفوعة في تطبيق Native دون خلطها مع:

- معاينة الكاميرا المحلية قبل الرفع.
- WebRTC والبث الحي.
- أي فيديو محلي لم يرفع بعد.

هذه المرحلة لا تعيد ترميز الملفات القديمة ولا تستبدل مصادرها.

## البنية المنفذة

### محلل مصدر مركزي

`library-media` يحدد نوع المصدر ويعالج:

- مفاتيح Object Storage القديمة.
- مسارات `/objects/...`.
- روابط API الخاصة.
- الروابط الخارجية العامة.
- الملفات المحلية `file:` و`content:` و`blob:`.

سياسة المصادقة:

- Native: رابط API بدون token في query، مع `Authorization: Bearer`.
- Web: query token لأن عنصر الوسائط في المتصفح لا يضمن إرسال Authorization header.
- لا يضاف token إلى مصدر خارجي غير تابع لـAPI التطبيق.

### مشغل canonical للملفات

المشغل المركزي يوفر:

- فيديو وصوت عبر `expo-video`.
- حالات تحميل وفشل وإعادة محاولة.
- مصدرًا بديلًا عند توفيره.
- تفاصيل تشخيصية آمنة لا تعرض token.
- إيقاف التشغيل عند إزالة المكوّن.
- تحديث موضع التشغيل.
- استئناف اختياري من آخر موضع محفوظ.

### محتوى الشريعة

- أزيل التشغيل المباشر الخاص بهذه الشاشة.
- تستخدم الشاشة المشغل المركزي.
- تحفظ الموضع والتقدم كل 10 ثوانٍ بدل إرسال mutation كل ثانية.
- تستأنف من `lastPosition`.
- يبقى اعتماد الإكمال اليدوي ومنطق تقدم الخادم كما هما.

## مصفوفة المستهلكين

| المستهلك | نوع المصدر | المسار |
|---|---|---|
| المكتبة | ملف خاص أو خارجي | المشغل المركزي |
| قراءة مادة مكتبة | ملف خاص أو خارجي | المشغل المركزي |
| تسجيلات المعلم | تسجيل خاص | المشغل المركزي |
| تسجيل جلسة الطالب | تسجيل خاص | المشغل المركزي |
| مراجعة المشرف لاختبار القبول | فيديو خاص | المشغل المركزي |
| ملف الطالب في الإدارة | فيديو خاص | المشغل المركزي |
| محتوى الشريعة | صوت/فيديو خاص أو خارجي | المشغل المركزي |
| معاينة تسجيل اختبار القبول قبل الرفع | ملف محلي | مشغل محلي منفصل عمدًا |
| معاينة onboarding للمعلم قبل الرفع | ملف محلي | مشغل محلي منفصل عمدًا |
| WebRTC والبث الحي | stream لحظي | خارج canonical file player عمدًا |

## الرفع والتحقق الخادمي

الرفع الحالي يحافظ على ملفات المستخدم كما هي، ثم يجري الخادم فحص سلامة:

- بنية MP4 ووجود `ftyp` و`moov`.
- بنية WebM.
- فحص كامل بواسطة `ffprobe`.
- رفض الملفات المبتورة أو stubs.

## ما لم ينفذ في هذه المرحلة

### Normalization/Transcoding

لا توجد بعد pipeline تعيد ترميز كل فيديو إلى:

- MP4
- H.264
- AAC
- `yuv420p`
- `+faststart`

ولم تضف حالات `processing/ready/failed` أو worker منفصل. لذلك التوافق البرمجي تحسن، لكن codec normalization المطلوب لكل ملف قديم وجديد ما زال PARTIAL.

### إثبات Range وAVPlayer

نجاح التصدير واختبارات بنية الملف لا يثبت أن:

- الخادم يعيد `206 Partial Content` لكل مصدر خاص في Production.
- `Accept-Ranges`, `Content-Range`, `Content-Length`, و`Content-Type` صحيحة في المسار المنشور.
- AVPlayer يشغل كل ملف قديم على iPhone.
- ExoPlayer يشغل كل ملف قديم على Android.

هذه البنود تحتاج بيئة staging وحسابات اختبار وأجهزة فعلية. لا توجد نتيجة device PASS في هذا التقرير.

## بوابة القبول المقترحة

1. اختيار عينة تشمل placement وsession recording وlibrary وsharia، مع ملفات MP4 وWebM قديمة وجديدة.
2. فحص headers بطلب Range مصادق في staging.
3. تشغيل العينة على iPhone صغير وحديث وعلى Android.
4. التحقق من seek والاستئناف وإعادة المحاولة وعدم ظهور token في logs أو URL على Native.
5. عدم الانتقال إلى Production/App Store build قبل إغلاق نتائج الفشل.
